# WeTalk_v3 结构化输出健壮性方案 v1

> 日期：2026-09-07
> 性质：方案建议稿，未改动代码。
> 背景：运行中发现千问模型偶尔把结构化结果包成数组（如 `[{"intent": "倾诉"}]`），
> 或带 ```json 代码块、前后缀解释文字，`with_structured_output` 直接校验崩溃。

## 0. 思路

容错解析解决的是"输出已经坏了怎么救"，治本需要五层：
提示层（少犯错）→ 调用层（走强约束通道）→ 解析层（schema 感知 + 语义兜底）
→ 重试与降级层（纠错 + 安全兜底）→ 观测层（失败率可量化）。

---

## 1. 提示层：先让模型少犯错（成本最低）

- **few-shot 示例**：每个结构化节点给 1~2 个"输入 → 正确 JSON"的例子；
- **负例声明**：明确写"不要输出数组、不要用 ```json 代码块、不要加解释"；
- **格式指令放 system 并前置**：放在历史上下文之前，避免被长历史稀释；
- **控制上下文长度**：classify 等判断节点注入历史后，长上下文可能诱发格式漂移。
  建议 A/B：同一批话术在"有历史 / 无历史"下的格式失败率；
  差异明显时缩短历史或把格式要求紧贴输出前。

## 2. 调用层：优先函数调用通道，而不是文本 JSON

- 对支持函数调用的模型，显式指定 `method="function_calling"`：
  把 Intent / CrisisRisk 声明成"工具"并强制 `tool_choice`，
  平台对 tool_calls 参数的 JSON 约束强于自由文本；
- 打开 `include_raw=True`，拿到 `{parsed, raw, parsing_error}`，
  即使解析失败也能保留原始输出做二次兜底，而不是抛异常。

```python
chain = qwen_llm.with_structured_output(
    Intent,
    method="function_calling",   # 前提：模型支持函数调用
    include_raw=True,
)
raw_result = chain.invoke(messages)
parsed = raw_result.get("parsed")
parsing_error = raw_result.get("parsing_error")
```

## 3. 解析层：schema 感知 + 语义兜底

### 3.1 已知缺陷：MemoryExtract 顶层数组会被静默丢弃

当前 `_parse_model_json` 见到数组一律取第一个元素：

- 对 Intent（`[{"intent": "倾诉"}]`）正确；
- 对 MemoryExtract **错误**：模型若直接输出顶层数组
  `[{"category": ..., "content": ...}, ...]`，解析器取第一条后
  校验 `MemoryExtract` 失败 → 返回空 → **记忆无声无息地丢失**。

修复方向：解析逻辑感知目标 schema 的形状——单对象 schema 取数组首元素；
"数组容器" schema（`items: [...]`）则把顶层数组直接包成 `{"items": [...]}`。

### 3.2 语义兜底（JSON 结构全烂也能救）

- **关键词扫描**：输出文本中直接出现"倾诉/闲聊/危机/求助"（危机为 high/normal）
  时按词命中返回，不依赖 JSON 结构；
- **Pydantic 放软校验**：`model_config = ConfigDict(extra="ignore")`；
  `intent` 字段加 validator 做归一化（"倾述/倾吐"→"倾诉"，大小写统一）。

## 4. 重试与降级层：给模型一次纠错机会，再按节点安全兜底

失败后把错误反馈回模型再问一次：

```python
for attempt in range(2):
    raw = qwen_llm.invoke(messages)
    parsed = _parse_model_json(raw.content, Intent)
    if parsed is not None:
        return parsed
    messages = messages + [SystemMessage(
        content="上次输出不是合法的 JSON 对象（例如包成了数组或加了代码块）。"
                "请只输出一个 JSON 对象，例如 {\"intent\": \"倾诉\"}。"
    )]
```

两次都失败才走降级。各节点降级策略不同，注意安全方向：

| 节点 | 降级策略 | 说明 |
|---|---|---|
| classify 意图判断 | 沿用上一轮 intent；无则默认"倾诉" | 宁可走陪伴路径，不崩请求 |
| crisis_check 危机复核 | 按"需关注/人工复核"处理，**不要默认 normal** | 当前默认 normal 对安全场景是危险方向 |
| remember 记忆提取 | 失败不写入可接受 | 但连续失败需日志告警，说明提取链路退化 |

## 5. 观测层：让格式失败变成可量化指标

- 把 `raw.content` 与解析结果写入日志（脱敏），统计每个节点的**格式失败率**，
  设阈值告警；
- 建立"刁钻输入"评测集（危机表达、追问、超长历史、混合情绪），
  每次改提示词/模型都跑回归，看意图正确率 + 格式成功率；
- 失败率持续高的节点优先排查：上下文过长、格式要求被挤到提示词尾部、
  或换更稳的模型（判断类节点值得用好一点的模型，因为它只有一次调用）。

## 6. 落地优先级

1. 调用层改 `function_calling` + `include_raw=True`；
2. 解析层改 schema 感知（修复 MemoryExtract 顶层数组丢记忆问题）+ 关键词兜底；
3. 加一次带反馈的重试；
4. 按节点调整降级方向（crisis_check 不再默认 normal）；
5. 建立格式失败率日志与评测集。
